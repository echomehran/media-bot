# Contributing

Thank you for contributing to Media Bot.

This document defines the engineering standards and contribution workflow for the project. Contributions should fit the existing architecture and maintain the project's code quality rather than simply producing a working result.

## Development Principles

Contributions should prioritize:

- Correctness
- Readability
- Maintainability
- Testability
- Consistency with the existing architecture
- Minimal and focused changes

Code should be written for the next developer who has to understand and maintain it, not only for the current task.

Avoid solutions that merely "work" when a clearer, simpler, or more maintainable implementation is available.

Do not introduce unnecessary abstractions, dependencies, patterns, or refactoring that are unrelated to the task.

Before adding new code, understand the existing implementation and follow its established conventions.

## Code Quality

New code should follow modern Python standards and the conventions already used in the project.

### Type Hints

Use type hints for functions, methods, parameters, and return values.

Prefer precise types over overly broad types such as `Any` when the actual type can be expressed.

### Docstrings

Public classes, functions, methods, and other reusable interfaces should have clear docstrings when their purpose or behavior is not obvious from the code.

Docstrings should explain the interface and important behavior, not restate the implementation.

Do not add meaningless docstrings such as:

```python
def get_user(user_id: int) -> User | None:
    """Get a user."""
```

Prefer documentation that explains non-obvious behavior, constraints, or important semantics.

### Naming and Structure

Use descriptive names and keep functions and classes focused.

Prefer small, cohesive units over large functions containing unrelated responsibilities.

Follow the existing project structure rather than introducing a new organizational pattern for a single feature.

Avoid:

- Dead code
- Unused abstractions
- Duplicate logic
- Magic values without justification
- Unnecessary comments
- Premature optimization
- Unrelated refactoring

Comments should explain why something is done when the reason is not obvious from the code. They should not simply describe what the code already says.

## Architecture

Media Bot separates Telegram interaction, application logic, data access, and infrastructure concerns.

The current dependency flow is:

```text
Telegram
   │
   ▼
Handlers
   │
   ▼
Application / Services
   │
   ▼
Repositories
   │
   ▼
SQLAlchemy
   │
   ▼
PostgreSQL
```

Keep responsibilities within their appropriate layer.

Handlers should handle Telegram-specific interaction and delegate application behavior.

Services should contain application-level use cases and should not depend on Telegram-specific implementation details.

Repositories should encapsulate database access.

Avoid putting database queries directly inside handlers or mixing infrastructure concerns into application logic.

New architectural patterns should have a clear reason and should be consistent with the project's existing design.

## Testing

Testing is a required part of a contribution, not an optional final step.

Any contribution that changes behavior should include appropriate tests.

Tests should verify behavior and important edge cases rather than merely increasing coverage numbers.

Use:

- `tests/unit/` for isolated application behavior
- `tests/integration/` for behavior involving external infrastructure such as PostgreSQL

When fixing a bug, add a regression test that would fail without the fix whenever practical.

When adding a feature, test:

- The expected behavior
- Important edge cases
- Failure behavior where relevant
- Interactions with dependencies when they are part of the feature

Tests should be deterministic, isolated, and easy to understand.

Do not weaken, remove, skip, or overly mock tests simply to make the test suite pass.

Do not make tests depend on the local development database.

Run the complete test suite before opening a pull request:

```bash
uv run pytest
```

## Database Changes

Database schema changes must be implemented through Alembic migrations.

After modifying database models, generate and review the migration:

```bash
uv run alembic revision --autogenerate -m "describe change"
```

Generated migrations must be reviewed manually. Do not assume an autogenerated migration is correct.

Apply migrations locally with:

```bash
uv run alembic upgrade head
```

Do not modify migration files that have already been applied to shared environments. Create a new migration instead.

Integration tests involving PostgreSQL should use the dedicated test database.

## Commit Messages

Media Bot follows Conventional Commits.

The format is:

```text
<type>(<scope>): <description>
```

The scope should identify the part of the project affected by the change when it adds useful context.

Examples:

```text
feat(users): add user service
fix(users): handle missing Telegram username
test(users): add repository integration tests
refactor(repositories): simplify user repository
docs(architecture): document repository boundaries
ci(tests): add PostgreSQL service
chore(deps): update dependencies
```

Use a meaningful scope rather than an arbitrary or overly broad one.

For example:

```text
feat: add user service
```

is acceptable when the scope would not add useful information, but:

```text
feat(users): add user service
```

is preferable when the affected area is clear.

Commit messages should describe the actual change clearly and concisely.

For non-trivial changes, the commit body should explain why the change was necessary when that context is not obvious from the subject.

Avoid vague messages such as:

```text
fix stuff
update code
changes
test
more changes
```

Keep commits focused on one logical change. Avoid mixing unrelated refactoring, formatting, documentation, and feature work in the same commit.

## Branches

Create branches from `main` and use descriptive names:

```text
feat/add-user-service
fix/user-lookup
refactor/repository-interface
test/user-service
docs/update-architecture
```

A branch should normally correspond to one issue or one clearly defined piece of work.

## Pull Requests

Pull requests should be focused, reviewable, and complete.

Before opening a pull request:

```bash
uv run ruff check .
uv run pytest
```

The pull request should:

- Explain what changed
- Explain why the change was needed
- Include appropriate tests
- Mention relevant design decisions
- Keep unrelated changes out of scope

Do not open a pull request containing known failing tests, lint errors, unfinished code, debug output, or temporary workarounds unless the pull request explicitly exists to address that issue.

Keep pull requests reasonably small. If a change becomes large because of an architectural decision, explain the reason in the pull request.

CI must pass before merging.

Pull requests are normally merged into `main` using Squash and Merge.

## Code Review

Code review is part of the development process, not merely a final approval step.

Reviewers may evaluate:

- Correctness
- Test coverage and test quality
- Readability
- Maintainability
- Architecture
- Error handling
- Database safety
- Type safety
- Consistency with project conventions
- Whether the complexity introduced is justified

A solution should not be accepted simply because it passes the tests.

Contributors should be prepared to revise an implementation when a simpler, clearer, safer, or more maintainable approach is identified during review.

## Before Submitting

Before opening a pull request, verify that:

```bash
uv run ruff check .
uv run pytest
```

both pass locally.

Also review your own diff:

```bash
git diff main...HEAD
```

Make sure the final diff contains only changes relevant to the contribution.

Check for:

- Debugging code
- Accidental files
- Unused imports
- Temporary comments
- Unnecessary refactoring
- Missing tests
- Poor or vague commit messages
- Changes that violate existing architectural boundaries

A contribution should leave the codebase at least as maintainable as it was before the change.

## Questions and Design Changes

If a contribution requires a significant architectural change, discuss the approach before implementing it.

For non-trivial changes, open or reference an issue so the problem, proposed approach, and scope can be discussed before substantial implementation work begins.

Small improvements that clearly follow existing patterns do not require unnecessary process.

When in doubt, prefer the simplest solution that satisfies the requirements while preserving the project's architecture and maintainability.
